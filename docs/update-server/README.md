# Update Server

Auto-update system for the GPUI desktop application. The client checks a remote manifest, downloads a newer build when available, and applies it on next launch.

## How It Works

```
App startup                        User triggers check
    |                                      |
    v                                      v
check_pending_swap()              check_for_updates()
    |                                      |
    v                                      v
Swap binary if marker       GET manifest.json, compare versions
    |                                      |
    v                                      v
App runs with latest        download_update() if newer
                                   |
                                   v
                           Stream to temp dir, verify codesign (macOS)
                                   |
                                   v
                           apply_update() writes pending-swap marker
                                   |
                                   v
                           Next launch: check_pending_swap swaps binary
```

1. **Check** -- The client fetches `manifest.json` from a remote URL and compares the manifest version against the running app version using strict semver ordering.
2. **Download** -- If a newer version exists, the user can trigger a download. The asset for the current `{os}-{arch}` platform key is streamed to a temp directory with progress reporting.
3. **Verify** -- On macOS, `codesign --verify --deep --strict` runs on the downloaded asset before accepting it.
4. **Apply** -- A pending-swap marker file is written. On the next app launch, the marker is read and the new binary (or `.app` bundle) replaces the current one.

## Manifest Format

The server hosts a `manifest.json` at a known HTTPS URL. Schema:

```jsonc
{
  // Required. Semver string. Must be strictly greater than the running
  // version to trigger an update.
  "version": "0.3.0",

  // Optional. Plain-text release notes shown to the user.
  "release_notes": "Bug fixes and performance improvements.",

  // Optional. Map of platform key to downloadable asset.
  "platforms": {
    "<platform-key>": {
      // Required. HTTPS URL to the downloadable binary or .app.tar.gz.
      "url": "https://releases.example.com/app-0.3.0-macos-aarch64.tar.gz",

      // Optional. Currently unused by the client but reserved for future
      // Ed25519 signature verification.
      "signature": "",

      // Optional. File size in bytes, used for logging.
      "size": 0
    }
  }
}
```

### Full Example

```json
{
  "version": "0.3.0",
  "release_notes": "Added dark mode support and fixed memory leak in query cache.",
  "platforms": {
    "macos-aarch64": {
      "url": "https://releases.example.com/gpui-starter-0.3.0-macos-aarch64.tar.gz",
      "signature": "",
      "size": 8523417
    },
    "macos-x86_64": {
      "url": "https://releases.example.com/gpui-starter-0.3.0-macos-x86_64.tar.gz",
      "size": 9134528
    },
    "linux-x86_64": {
      "url": "https://releases.example.com/gpui-starter-0.3.0-linux-x86_64.tar.gz",
      "size": 7891234
    },
    "windows-x86_64": {
      "url": "https://releases.example.com/gpui-starter-0.3.0-windows-x86_64.zip",
      "size": 8245671
    }
  }
}
```

## Platform Keys

The client constructs its platform key as `{os}-{arch}` at compile time:

| OS           | `target_os`   | Architecture | `ARCH`     | Platform Key       |
|--------------|---------------|-------------|------------|--------------------|
| macOS        | `macos`       | ARM 64-bit  | `aarch64`  | `macos-aarch64`    |
| macOS        | `macos`       | Intel       | `x86_64`   | `macos-x86_64`     |
| Linux        | `linux`       | Intel       | `x86_64`   | `linux-x86_64`     |
| Linux        | `linux`       | ARM 64-bit  | `aarch64`  | `linux-aarch64`    |
| Windows      | `windows`     | Intel       | `x86_64`   | `windows-x86_64`   |
| Windows      | `windows`     | ARM 64-bit  | `aarch64`  | `windows-aarch64`  |

The key is generated by `platform_key()` in `src/services/updater.rs`. The `os` segment comes from `cfg!(target_os)` and the `arch` segment from `std::env::consts::ARCH`. If the manifest has no entry for the current platform key, the download will fail with a "no asset for platform" error.

## Version Comparison

Versions are parsed with the [`semver`](https://docs.rs/semver) crate. The comparison is strict:

```rust
if manifest_ver > cur_ver {
    // Update available
} else {
    // Up to date (equal or older manifest)
}
```

- Only a manifest version **strictly greater than** the running version triggers an update.
- Pre-release tags are respected per the semver spec (`1.0.0-alpha` < `1.0.0`).
- If either version fails to parse, the check fails with an error.

## macOS Codesign Verification

After downloading, the updater runs:

```
codesign --verify --deep --strict <downloaded-path>
```

This verifies the downloaded binary or `.app` bundle against the system trust store. Requirements:

- The released binary must be signed with a valid Developer ID certificate.
- If the signature check fails, the update is rejected and the user sees an error.
- The `signature` field in the manifest is reserved for future Ed25519-style verification but is not currently checked.

## Hosting: GitHub Pages

The simplest way to host the manifest.

### 1. Create a `gh-pages` branch

```bash
git checkout --orphan gh-pages
git rm -rf .
echo '{}' > manifest.json
git add manifest.json
git commit -m "Initialize gh-pages with empty manifest"
git push origin gh-pages
```

### 2. Enable GitHub Pages

Go to **Settings > Pages** in your GitHub repo and set:

- **Source**: Deploy from a branch
- **Branch**: `gh-pages` / `/ (root)`

The manifest will be available at:
```
https://<org>.github.io/<repo>/manifest.json
```

### 3. Auto-update on release

Add a step to your release workflow (e.g., `.github/workflows/release.yml`) that regenerates and commits the manifest:

```yaml
- name: Update manifest on gh-pages
  run: |
    git checkout gh-pages
    cat > manifest.json <<EOF
    {
      "version": "${{ github.event.release.tag_name }}",
      "release_notes": "$(jq -r '.body' <<< '${{ toJson(github.event.release.body) }}')",
      "platforms": {
        "macos-aarch64": {
          "url": "https://github.com/${{ github.repository }}/releases/download/${{ github.event.release.tag_name }}/app-macos-aarch64.tar.gz",
          "size": $(curl -sI "https://github.com/${{ github.repository }}/releases/download/${{ github.event.release.tag_name }}/app-macos-aarch64.tar.gz" | grep -i content-length | awk '{print $2}' | tr -d '\r')
        }
      }
    }
    EOF
    git add manifest.json
    git commit -m "Update manifest for ${{ github.event.release.tag_name }}"
    git push origin gh-pages
```

### 4. Override the manifest URL

Set the compile-time environment variable when building the client:

```bash
GPUI_UPDATE_MANIFEST_URL=https://myorg.github.io/myrepo/manifest.json \
  cargo build --release
```

The default URL is `https://releases.example.com/manifest.json`, defined as `DEFAULT_MANIFEST_URL` in `src/services/updater.rs`. Point it at your actual manifest location.

## Hosting: Custom Server

You can host `manifest.json` on any static file server. Requirements:

- **HTTPS only.** The client uses `reqwest` and expects valid TLS.
- **CORS.** Not required -- the client makes a direct HTTP GET, not a browser fetch.
- **No authentication.** The manifest must be publicly accessible.
- **Content-Type.** Should be `application/json`, though the client does not enforce this.

Example nginx config:

```nginx
server {
    listen 443 ssl;
    server_name releases.example.com;

    ssl_certificate     /etc/ssl/certs/releases.example.com.pem;
    ssl_certificate_key /etc/ssl/private/releases.example.com.key;

    root /var/www/releases;

    location /manifest.json {
        add_header Cache-Control "no-cache";
    }
}
```

Place `manifest.json` and release assets in `/var/www/releases/`. Update the manifest after each release by rewriting the file with the new version and asset URLs.

## Compile-Time Override

The manifest URL is baked into the binary at compile time. Override it by setting the `GPUI_UPDATE_MANIFEST_URL` environment variable before building:

```bash
# Staging
GPUI_UPDATE_MANIFEST_URL=https://staging.example.com/manifest.json cargo build

# Production
GPUI_UPDATE_MANIFEST_URL=https://releases.example.com/manifest.json cargo build --release
```

To change the default permanently, edit `DEFAULT_MANIFEST_URL` in `src/services/updater.rs`.

## Security Considerations

| Concern            | Mitigation                                                |
|--------------------|-----------------------------------------------------------|
| Transport          | HTTPS required. Plain HTTP will fail on certificate check.|
| Binary integrity   | macOS codesign verification via `codesign --verify`.      |
| Downgrade attacks  | Strict semver comparison rejects older manifest versions. |
| Manifest tampering | The `signature` field is reserved for future verification.|
| Local tampering    | Pending-swap marker uses a predictable path under the     |
|                    | platform data directory (`~/Library/Application Support/` |
|                    | on macOS).                                                |
| No authentication  | The manifest and assets are public. No API keys needed.   |

The system currently trusts the HTTPS transport and macOS codesign chain. For stronger guarantees, populate the `signature` field with an Ed25519 signature and verify it client-side (not yet implemented).
